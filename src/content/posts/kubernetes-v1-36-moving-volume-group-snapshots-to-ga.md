Volume Group Snapshots reached General Availability (GA) in Kubernetes v1.36 under the `groupsnapshot.storage.k8s.io/v1` API group. This feature allows users to take crash-consistent snapshots across a set of PersistentVolumeClaims (PVCs) at the exact same point-in-time. 

### Architectural Significance

For stateful applications spanning multiple volumes (e.g., database data files on one volume and write-ahead logs on another), standard individual `VolumeSnapshot`s are insufficient. Taking sequential snapshots introduces timing deltas, resulting in inconsistent state upon recovery unless the application is quiesced (I/O paused) prior to snapshotting.

Volume Group Snapshots solve this by delegating point-in-time consistency across multiple disks to the underlying storage array, removing the need for application-level quiescence. 

**Constraints:**
- **CSI-Exclusive:** This relies strictly on Container Storage Interface (CSI) drivers. Both the storage backend and its CSI driver must support group snapshots.

### API Primitives

The feature introduces three CustomResourceDefinitions (CRDs) that mirror the design of the standard VolumeSnapshot APIs:

- **`VolumeGroupSnapshot`**: User-facing intent to snapshot multiple PVCs, matched via a label selector.
- **`VolumeGroupSnapshotContent`**: The cluster-scoped resource provisioned by the snapshot controller representing the physical group snapshot on the storage backend.
- **`VolumeGroupSnapshotClass`**: Administrator-defined configuration specifying the CSI driver and lifecycle parameters (e.g., deletion policy).

### Implementation

To capture a group snapshot, group the target PVCs using a common label:

```bash
kubectl label pvc data-pvc group=myGroup
kubectl label pvc log-pvc group=myGroup
```

Define a `VolumeGroupSnapshotClass` bound to a capable CSI driver:

```yaml
apiVersion: groupsnapshot.storage.k8s.io/v1
kind: VolumeGroupSnapshotClass
metadata:
  name: csi-group-snapclass
driver: example.csi.k8s.io
deletionPolicy: Delete
```

Create the `VolumeGroupSnapshot` specifying the label selector to execute the snapshot:

```yaml
apiVersion: groupsnapshot.storage.k8s.io/v1
kind: VolumeGroupSnapshot
metadata:
  name: db-snapshot-20260422
  namespace: demo-namespace
spec:
  volumeGroupSnapshotClassName: csi-group-snapclass
  source:
    selector:
      matchLabels:
        group: myGroup
```

### Restoring from a Group Snapshot

There is no dedicated "Group Restore" primitive. Instead, restoring involves rehydrating individual volumes from the distinct `VolumeSnapshot` objects generated as part of the group snapshot operation.

*Note: You must explicitly recreate every PVC in the group from its corresponding `VolumeSnapshot` to guarantee cross-volume consistency.*

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc-restored
  namespace: demo-namespace
spec:
  storageClassName: example-sc
  dataSource:
    # Must reference the specific VolumeSnapshot generated by the VolumeGroupSnapshot
    name: snapshot-0962a745b2bf930bb385b7b50c9b08af471f1a16780726de19429dd9c94eaca0
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOncePod
  resources:
    requests:
      storage: 100Mi
```

### CSI Driver Requirements

Storage vendors must update their CSI drivers to support this feature by:
1. Implementing a group controller service.
2. Implementing the RPCs: `CreateVolumeGroupSnapshot`, `DeleteVolumeGroupSnapshot`, and `GetVolumeGroupSnapshot`.
3. Advertising the `CREATE_DELETE_GET_VOLUME_GROUP_SNAPSHOT` controller capability.
